# Known limitations

[中文](known-limits.md) | **English**

This page has two parts:

- **Evidence gaps:** areas our current validation does not extend to;
- **Feature boundaries:** things deliberately left out, or implemented only in a minimal form.

Each item tries to say when you will run into it and how to work around it.

## Evidence gaps

1. **Requester sign-off has only automated test coverage.** When the requester is on the sign-off list, the owner's approval counts as one vote and the system must still wait for the requester to sign off in person. This rule has not been validated in real multi-user use. If sign-off stays pending, first check whether it is waiting for the requester.
2. **Live validation used only a few models:** DeepSeek, and Kimi called through OpenRouter. Anthropic, OpenAI and Gemini have only adapter-level validation (single-turn conversation and tool-call loops). Evidence that the agent asks questions, the reviewer sends work back and corrections go through comes from the first two. Try a small task before switching vendors.
3. **Only small projects have been validated.** The largest samples were medium-sized open-source libraries (a few thousand lines) and small applications built from scratch. There are no multi-day tasks and no large repositories. Only Node and Python have been validated.
4. **There is no long-term real-team data for multi-user collaboration.** Multi-user flows were validated only through simulated use. How often a real team would be interrupted or misrouted over a week is unknown.
5. **MCP, policy hooks, the GitHub loop and reply by email have only automated test coverage.** They have not yet been used over time by real teams on real repositories. The first time you use them, try a round on a small project.

## Feature boundaries

1. **Access and authentication**
   - **Local mode (default):** the web UI listens only on 127.0.0.1. Requests without a token act as the administrator who started the web UI, so other local processes can also call the API as that administrator. The server checks `Host` and origin; this protects against other websites using your browser to send requests, not against local processes.
   - **Team mode:** intended for intranets, not the public internet. For what it protects against and what it does not, see [Team deployment](deploy-team.en.md).
2. **What can be answered from a notification is limited:** every push links to its item, where spec choices, structural conflicts, system-stuck items and disagreements can be answered directly; sign-offs, security approvals, plan approvals, limit increases, network approvals and delivery need the full task page. Replying by email works only for spec choices, structural conflicts and system-stuck items. ntfy, Feishu, DingTalk and WeCom have no answer buttons.
3. **Context compaction is a safety net, not the normal path:** when a single request passes the "Automatic compaction line" (120k tokens by default), the system first removes old tool outputs, and if that is not enough, has the model write a brief and rebuilds the context from it. The brief loses details; if one step still does not fit after two compactions, the system suggests splitting the step. The context limit is 150k tokens by default, and models with a context window recorded in the catalog are also capped by that window. When binding a model with a small window, lower the limit under "Budget & limits"; the compaction line is then pushed down to 80% of the limit.
4. **Retrieval is limited to the repository map:** each step starts with a map of files and symbols ranked by scope, as of the start of the step and not refreshed when files change mid-step; beyond that, the agent uses grep and reads files. There is no full-text or semantic index, so with a very large repository the context can still run out first. Without Universal Ctags, definitions are found with per-language patterns covering JS/TS, Python, Go, Rust, the Java family, Ruby, PHP and C/C++.
5. **There are only two sandbox images:** Node, and Python (with Chromium for screenshots). The agent must install dependencies for other languages inside the sandbox itself (the project must allow the corresponding network domains). Podman and rootless Docker have not been validated.
6. **Page checks have limits:** page screenshots before sign-off capture only the page right after it finishes loading. When the reviewer checks the running app, it can open pages, click, type and select, but drag and drop, hover menus, file uploads and multiple tabs are not supported. It needs the Python sandbox image with Chromium and `si-preview.json` at the repository root. Only models marked vision get screenshots; models you add to the catalog yourself are always treated as not accepting images.
7. **Test protection recognizes only three languages:** the handoff comparison of "were pre-existing tests weakened" recognizes JavaScript, Python and Go test styles; test changes in other languages are not flagged. "Send back directly when tests are weakened" can currently be turned on only from the CLI.
8. **Prices are estimates:** costs use the prices recorded in the model catalog. DeepSeek is recorded at peak prices, so off-peak usage actually costs less. The vendor's bill is authoritative.
9. **Conflict detection covers one item at a time:** if two people's answers to different questions contradict each other semantically (A's answer to Q1 implies X, B's answer to Q2 implies not-X), the system does not detect it.
10. **The AI's own assumptions are not compared across tasks running at the same time:** when several tasks in one project run concurrently, the small decisions each executor makes are checked for conflicts only within its own task. If two tasks settle on contradictory approaches (an error-code format, for example), it may only surface in the tests after merging or at sign-off. Conventions a person has decided are passed to every task, but a task already running sees them only from its next step. If a project has conventions that tasks could easily settle differently, write them into the contract or a decision first.
11. **Task dependencies cannot be changed in the UI once created:** dependencies and ordering can be specified when adding a task, but there is no UI for editing dependencies between existing tasks.
12. **Similar items are grouped, not merged:** digests and the Inbox place items of the same kind from the same project together, but the system does not judge whether several items ask the same thing, and they cannot be answered in one go. Duty handover follows the rotation plus covers (someone covers whole days); holidays affect only "1bd" and working hours, and do not pause the duty roster. The rotation list cannot be reordered by dragging; remove people and add them again instead.
13. **Working hours fall back to UTC:** if neither the person nor the deployment has a time zone set, working hours and status report times use UTC, which is 8 hours off for a deployment in China; "My notifications" only warns when the browser's time zone differs. Administrators should set the deployment time zone under Time and calendar first.
14. **Mailbox limits for reply by email:** Gmail and Outlook.com IMAP need an app password (OAuth2 login is not supported). Mailboxes without plus addressing (such as QQ or 163) rely on the reply's In-Reply-To header to identify the item; a few clients drop it, and the sender then gets an email saying the item could not be identified and should answer on the board instead.
15. **Limits of project rules and extensions:**
    - **Project rules** go only to the executor and the reviewer and are not read during planning; rules edited on the board are not seen by tasks already started (their workspace was branched from the project branch when they started), and apply from tasks started afterwards.
    - **Skills:** `allowed-tools`, `paths` and `context: fork` are recorded but have no effect; the reviewer and the planner do not get skills.
    - **Hooks** do not support `updatedInput` (they cannot rewrite what the AI does); only PreToolUse is read from `.claude/settings.json`; built-in checks (writable paths, shared paths, rules and hook files, review, sign-off, push guardrails) cannot be turned off or replaced by hooks; hook run history is only in the audit log, not on the board.
    - **MCP** uses only a server's tools; requests from the server to call a model, list directories or ask the user are refused. Servers run only in the sandbox, so tasks without a sandbox get no MCP tools. Read-only / write annotations from the tools cannot be trusted, so every tool needs approval on each call by default.
16. **Approval gates match command text:** commands the AI runs directly (including those wrapped in `sh -c` or chained with `&&`) are caught; commands run from inside scripts or programs are not seen, and a different way of writing the same operation is not caught (for example running ALTER TABLE through psql instead of a migrate command). To be safe, list the whole tool (such as `psql*`), at the cost of approving read-only uses too.
17. **Limits of the GitHub loop:** GitHub only; issues are polled every 5 minutes and there is no generic webhook intake; GitHub is only read, with no comments or label changes; fixing CI and acting on reviews share one "AI follow-up" switch and cannot be turned on separately; for whole-project PRs, someone must deliver the project again after the fix task merges for the PR to update.
18. **Redoing steps and widened scope cannot be taken back:**
    - **"Redo from this step" cannot be undone with one click:** only the task owner can use it, and only on finished steps; tasks that are delivered, merged into the project branch, aborted or archived are excluded (add a task instead). The code from before is kept at `refs/superintern/rewound/<id>` and must be retrieved with git.
    - **Approved scope extensions cannot be withdrawn:** once you approve the AI's request to widen its writable paths, they are written into the contract and there is currently no way to take them back.
19. **Status reports list only titles for "decided without waiting for you":** what was decided is not shown, so open the entry to see it. Reports are not written by a model and cannot be sent to people outside the team.
20. **WSL2 does not stay running on its own:** a WSL2 distribution does not start at Windows login and stops soon after the last session exits. See [WSL2 notes](deploy-linux.en.md#wsl2-notes) for keeping it running.
21. **Language boundaries:** the web UI, CLI, item content and AI text written for people support Chinese and English, with a few things to know:
    - **Content language is deployment-wide:** a team has only one content language (item content, reports and so on); each person can choose only their own interface language. Changing the content language affects only content written afterwards; existing items keep their original language.
    - **When the interface and content languages differ**, some error messages contain content-language fragments (the error's wrapper is in your language; names quoted inside it are in the content language).
    - **Model prompts are still in Chinese**, ending with an instruction to "write text intended for people in English". English output depends on the model following that instruction; live validation was done mainly in Chinese.
    - A few CLI diagnostic reports (replay, the permissions overview, the model catalog check) still output Chinese.
    - The README, the deployment guides and the known limitations have English versions; some other text in the repository is still in Chinese.
