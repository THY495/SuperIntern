# 部署

同一份代码支持三种部署形态：

| 形态 | 守护进程怎么常驻 | 说明 |
|---|---|---|
| Windows 10/11 + Docker Desktop | 计划任务：`scripts/daemon.ps1` | 本页 |
| Linux 主机 | systemd 用户单元：`scripts/daemon.sh` | [deploy-linux.md](deploy-linux.md) |
| WSL2 | 同 Linux，另外要在 Windows 侧挂一个不退出的 wsl 会话 | [deploy-linux.md](deploy-linux.md#wsl2-特有) |

多人从各自电脑登录（团队模式），见 [deploy-team.md](deploy-team.md)。

## 共同前置

- Node **≥ 22.13**（需要不带 flag 就能用的 `node:sqlite`；在 24.x 与 26.x 上验证过）和 git。**建议选自带 SQLite ≥ 3.51.3 的 Node 发行版**（Node 24.15.0 及以后的 24.x、以及 26.x 都满足；22.x 目前还不满足）：更早的 SQLite 在 WAL 模式下多个进程同时写时，有极小概率把库写坏（见 sqlite.org/wal.html）。看板与守护进程启动时检测到会提示，看板上只给管理员看。
- 容器运行时：docker 或 podman（podman 与 rootless docker 尚未验证）。跑守护进程的用户要能直接访问 docker socket。
- 首次安装：`scripts/setup.ps1` 或 `scripts/setup.sh`。它会做这些事：
  - 检查上面的前置条件；
  - 从 `.env.example` 生成 `.env`；
  - 构建沙箱镜像 `superintern/sandbox:v0.1` 和 `superintern/sandbox:v0.3-python`；
  - 拉取出网代理镜像 `mitmproxy/mitmproxy`。

  每个任务的出网代理镜像 `superintern/sandbox:ca-*` 会在第一次用到时自动构建，可以用 `node src/cli.mjs sandbox --reap` 清理。
- `.env`（权限 600，不要提交）：
  - **模型 key**：至少填一家厂商的 key。
  - **`GITHUB_TOKEN`**：老部署的写法，仍然有效。新部署建议在「设置 → 连接」里配交付用的凭据，见下文[连接](#连接交付用的凭据)。
  - **`NTFY_URL` 等**：部署级的通知通道。每个人自己的通道在「设置 → 成员」里挂。
  - **邮件（可选）**：`SMTP_URL`、`MAIL_FROM`（发信），`MAIL_TO`（部署级收件邮箱），`IMAP_URL`、`MAIL_REPLY_TO`（邮件答复），见下文[邮件通道与邮件答复](#邮件通道与邮件答复)。

  检查 key 时只看填没填，不要打印值：`grep -c '^DEEPSEEK_API_KEY=.' .env`。想读别的环境文件，设 `SUPERINTERN_ENV_FILE=<路径>`；设成 `none` 就不读 `.env`。
- 可选：主机上装了 Universal Ctags 时，仓库地图（见下文「模型与验收」）用它抽取符号；没装也能用，按语言用正则抽。
- 建库：`node src/cli.mjs init --name <管理员名字>`。它会做这些事：
  - 签发 CLI 令牌，写到 `.superintern/cli-token`。这是令牌唯一的明文副本，库里只存哈希。
  - 按 `.env` 里已有的 key 为 light / standard / heavy 三档选模型，也可以用 `--bind heavy=<服务商/模型>` 指定。

  库已经存在时，`init` 只跑迁移。
- 服务商、模型和档位绑定，之后都在看板「设置」里改，或者用 `endpoint` / `catalog` / `bind` 命令改。每次改动都记审计。

## Windows：计划任务

```powershell
powershell -ExecutionPolicy Bypass -File scripts\daemon.ps1 install
powershell -ExecutionPolicy Bypass -File scripts\daemon.ps1 status   # 也可以是 start | stop | uninstall
```

- **任务与日志**：任务名是 `SuperIntern Daemon`，登录即启动。另有一个每 5 分钟的「拉活」触发器：进程在跑就忽略，死了才拉起来。日志在 `.superintern/logs/daemon.log`。
- **启动方式**：计划任务经 `wscript.exe` 以隐藏窗口启动 `daemon-launch.vbs`，再由它启动 `node src/cli.mjs web --daemon`，并等待它退出。这样做有两个原因：
  - 不会弹出控制台窗口。如果有窗口，被人关掉时进程会跟着死。
  - 进程不会在计划任务回收时被连带杀掉。
- **Docker Desktop**：要在登录会话里开着。从开机到 docker 就绪之间，第一轮任务会启动失败并进入 5 分钟退避，之后自动恢复。
- **不要同时装两份**：不要在同一台机器上既装 Windows 计划任务版，又装 WSL2 里的 systemd 版。两者会抢同一个端口，还会各自维护一份库。

## 看板

- 本机模式只监听 `127.0.0.1:7357`。远程访问走 SSH 隧道：`ssh -L 7357:127.0.0.1:7357 <host>`，然后在本机打开 http://127.0.0.1:7357/。
- 本机模式下不带令牌的请求，按启动看板的那个管理员执行。其他成员在看板上用自己的令牌登录：「设置 → 成员」里加人时会生成令牌，只显示一次。
- 多人从各自电脑直接访问，请用团队模式：[deploy-team.md](deploy-team.md)。
- **暂停全部（急停）**：管理员在看板顶栏点「暂停全部」，系统不再开始新的步骤，正在进行的步骤立即停下：进行中的模型调用当场取消，正在跑的命令跑完为止，这一步写到一半的改动先收起来、恢复后放回接着做。不算失败、不计重试，任务也不会被取消；点「恢复自动运行」后自动接着跑。暂停状态存在库里，重启照样生效。命令行：`node src/cli.mjs user setting deploy.paused true`（`false` 恢复）。
- **暂停 / 中止一个任务**：在 AI 的下一轮就生效，不等这一步连同验收做完。中止会当场取消进行中的模型调用。被打断那一步写到一半的改动存进 `refs/superintern/parked/<步骤>`，下次开跑时放回；放不回时，步骤里写明它在哪、怎么取。谁能点：暂停 = 负责人和参与过这个任务的人（事项发给过他，或他答过）；继续 = 负责人或按暂停的那个人；中止 = 只有负责人。`say --urgent` 发的修正或新指令同样会打断当前步骤、马上重新规划；补充信息不用加 `--urgent`，在执行中途就会送到 AI 手上。
- **从这一步重来**：任务负责人在步骤详情点「从这一步重来…」（只对做完的步骤）。这一步，连同用到它结果的步骤、提交排在它之后的步骤，一起退回重做，代码回到这一步之前。确认前先看预览：退回哪几步、哪些文件回到旧样子或被删、撤回哪些事项、哪些签收作废。退回前的代码（连同没提交的改动）留在 `refs/superintern/rewound/<id>`，不删。正在跑的任务要先暂停；已交付、已合并进项目分支、已中止或归档的任务不能这样退，要改请添加任务。命令行：`rewind <任务> <步骤> [--note "这次要注意什么"] [--yes]`，不带 `--yes` 只看预览。
- **AI 申请扩大可动路径**：交接只因为改了可动路径之外的文件被拒时，AI 可以申请把这些路径加进来。系统发一条方案批准事项，写明要加的路径、AI 给的理由、现在和批准后的可动路径、与同项目其它任务范围的重叠，以及范围外改动的 diff。选「批准」就写进契约，这一步的改动原样保留、不用重做；别的答复都算不批。共享路径、规则文件和钩子文件不能这样申请。

## 模型与验收

每次模型调用都属于一个**角色**：规划、执行、验收、写汇报等。每个角色默认用一个**档位**（light / standard / heavy），档位再绑到具体模型。

- **按角色单独绑定**：「设置 → 模型分配」的「各角色用哪个模型」表，或 `node src/cli.mjs bind role <角色> <服务商/模型>`（`bind role <角色> tier` 回到档位）。`bind show` 列出各角色现在用的是什么。
- **验收员换一家**：验收员没有单独绑定、而它的档位与这一步的执行器是同一家出品方时，系统自动换另一家的模型来验收。"同一家"按模型出品方算，经网关调用的模型按名字前缀算（`moonshotai/kimi-k3` 算 moonshotai）。`.env` 里只有一家的 key 时不换。在同一张表下面可以关掉（`deploy.verifier_vendor same`）。
- **两家会签**：同一处还可以让规划时标为高风险的步骤由两家各验一次，都通过才算过（`deploy.verifier_cosign high_risk`，默认关）。
- **备用模型**：每个档位可以配一个备用模型（「模型分配」的「备用」列，或 `bind fallback <档位>=<服务商/模型>`，`none` 去掉）。某家服务商连续出错时，系统暂停调用它一段时间（所有进程共用这个判断，冷却时间逐次加倍、最长 15 分钟），这期间有备用的档位自动换过去，恢复后换回。没有备用的步骤会等着，运行状况的「模型服务商」一项写明在等哪家。
- **原有测试被改弱**：每一步交接时，系统对比这一步对任务开始前就有的测试做了什么：删掉测试文件、加了跳过、用例或断言变少、改了期望值。默认只标出来，交给验收员和签收的人看；想让这种交接直接被打回，运行 `node src/cli.mjs user setting deploy.test_guard reject`（目前没有页面开关）。确实需要改时，答复那一条事项时勾「允许这一步改这些任务开始前就有的测试」，或命令行 `answer <事项> "…" --allow-tests`。目前认得 JavaScript、Python 和 Go 的测试写法。
- **上下文整理**：一次请求的上下文超过「自动整理线」时，系统先整理再接着跑：先把最早的大段工具输出换成一行占位（命令的完整输出另存在工作区的 `.si-outputs/`，不进提交），还不够再让模型写一份简报、按简报重建上下文。同一步整理两次还装不下，会发一条事项建议把这一步拆小。整理线在任务页或项目设置的「预算与上限」里改，默认 120k token，0 = 关闭；实际生效的不会超过上下文上限的 80%。
- **仓库地图**：执行器每一步开头拿到一张"文件 → 定义的符号"的图，按这一步的范围排序，截到 `deploy.repo_map_tokens`（默认 2048 token，0 = 不给）。地图是这一步开工时的样子，中途改了文件不重算。主机上装了 Universal Ctags 就用它抽符号，否则按语言用正则（JS/TS、Python、Go、Rust、Java 系、Ruby、PHP、C/C++）。

### 验收员在运行中的应用上点验

改了界面的步骤，规划时会写几条**界面条目**（"点删除后列表少一行"这一类，每步最多 8 条）。验收员会把应用起起来，在页面上打开、点、填、选，逐条给出"通过 / 不通过 / 没验成"，有一条不通过就打回。

- **要满足的条件**：任务在沙箱里跑，用的是带 Chromium 的 Python 镜像（项目默认就是；改成 `project sandbox <id> node` 的项目验不了，会记成"没验成"）；仓库根目录有 `si-preview.json`，写明怎么起服务。这份文件由 AI 自己维护：有界面条目的步骤交接时缺了它或写错，会被打回。
- **`si-preview.json`**：`start`（起服务的命令，最多 3 条）、`url`（只能是 `http://127.0.0.1` 或 `localhost`）必填；`ready`（起好之后要能访问的地址）、`seed`（写样例数据的命令）、`pages`（要看的页面）、`waitMs` 选填。签收前的页面截图用的也是它。
- **`SI_PREVIEW=1`**：系统起服务、写样例数据时都带这个环境变量。样例数据脚本会先检查它，没有就拒绝运行，免得把示例数据写进真在用的库；后端也可以据此换一个预览专用的库。签收卡上"自己把应用跑起来看"的命令也带着它。
- **看得到 AI 点了什么**：每次点、填之后自动存一张画面，验收员下结论时引用的留下（每条最多 3 张），其余删掉。步骤详情的「页面点验」逐条显示结论和画面；签收卡「页面截图」下面有「AI 验收时在页面上点过的」。没验成的条目会进签收卡「签收前先看这些」，要你自己核对。
- 应用起不来时，所有条目记"没验成"并附上原因，不会因此判失败。不支持拖拽、悬停菜单、上传文件和多标签页。截图工具只给收图的模型（模型目录里标了 vision 的；`catalog check --vision` 可以实测），其它模型只读页面文字。

## 连接（交付用的凭据）

交付会把分支推到远端仓库，还可以顺带开 PR。推送和开 PR 用的凭据叫"连接"，在看板「设置 → 连接」里管理，也可以用 `node src/cli.mjs cred` 管理。

- **不挂在项目上**：每次交付时，系统按"远端地址 + 谁点的交付"现场挑一份连接，审计里记下用的是哪一份。同一个组织下的项目不用逐个配置。
- **挑选顺序**：
  1. 点交付的人自己的连接。成员自己的连接只用于本人点的交付，别人点的交付不会借用；
  2. GitHub App；
  3. 部署级的令牌或 SSH 密钥；
  4. `.env` 里的 `GITHUB_TOKEN`（老部署）。

  同一档里有几份都匹配时，适用范围写得越具体越先（`acme/web` 先于 `acme/*`），再按新加的先。过期的连接、推送时被拒（权限不够）的连接会自动跳过，换下一份。连接的适用范围要和它在 GitHub 上实际授权的仓库对上。都用不上时，会试服务器上 git 自己配的凭据（一般没有）。想让 GitHub App 排在最前（PR 一律显示为 bot），管理员在「设置 → 连接」里改，或运行 `node src/cli.mjs user setting deploy.credential_order app_first`。
- **SSH 密钥只管推送**：开 PR 要调 GitHub 接口，系统会按同一仓库的 https 地址另挑一份 GitHub App 或令牌。
- **只支持在 GitHub 上开 PR**：GitLab、Gitea 和内网服务能推送，但不会自动开合并请求。
- **吊销只在本系统里生效**：GitHub 上的令牌或 App 私钥本身仍然有效，要作废请到 GitHub 上撤销。
- **存储**：连接加密存在状态库里（AES-256-GCM）。主密钥是 `.superintern/master.key`，第一次添加连接时生成；也可以用环境变量 `SUPERINTERN_MASTER_KEY` 提供。录入之后任何人都看不到值，页面上只显示末 4 位或密钥指纹。
- **交付前预检**：点交付时，看板会先查会用哪份连接、能不能推送，不通过就先问你。也可以在「设置 → 连接 → 检查一个远端」里单独查，或者运行 `node src/cli.mjs cred check <远端地址>`。
- **到期提醒**：填了到期日的连接，7 天内到期时会出现在主人的待办里；部署级的连接提醒管理员。GitHub 个人令牌没填到期日的话，检查一次之后系统会从 GitHub 读到并记下。
- **成员停用**：成员被停用时，这个成员自己的连接一并吊销。

### 用 GitHub App（仓库集中在一两个组织时推荐）

1. 在组织的 Settings → Developer settings → GitHub Apps → New GitHub App 新建一个 App：
   - Homepage URL：填组织主页，例如 `https://github.com/<组织名>`；
   - Webhook：取消勾选 Active；
   - Repository permissions：Contents、Pull requests 设为 Read and write，Metadata 保持 Read-only。要允许 AI 修改 `.github/workflows/` 下的文件，再把 Workflows 设为 Read and write。要让系统盯交付的 PR（见下文「GitHub 闭环」），再把 Checks、Commit statuses、Actions 设为 Read-only；要用 GitHub issue 入口，再把 Issues 设为 Read-only。已经装好的 App 加了权限之后，要到组织的 GitHub Apps 安装页接受新权限；
   - Where can this GitHub App be installed：选 Only on this account。
2. 建好后记下 App ID，点 Generate a private key，下载 `.pem` 私钥文件。
3. 在 App 页面左侧点 Install App，装到组织上，选全部仓库或指定仓库。
4. 在看板「设置 → 连接」添加一条 GitHub App 连接，填 App ID、贴入 `.pem` 的全部内容。也可以在服务器上运行：

   ```bash
   node src/cli.mjs cred add github-app --name "<组织名> App" --app-id <App ID> --key-file <pem 文件路径> --repos '<组织名>/*'
   ```

   录入之后可以删掉 `.pem` 文件。

每次推送时，系统用私钥现签一个临时令牌：只覆盖这一个仓库，权限按这次动作给，1 小时后过期。系统不长期保存任何 GitHub 令牌。推送和 PR 会显示为这个 App。

### 推送护栏

不管用哪份连接，系统都只往远端推它自己的分支（`superintern/…` 和 `v0/…`）：

- 不推远端的默认分支，不强推，不删分支；
- 远端分支上有别人推的提交时，停下来说明原因，不覆盖；
- 唯一的例外：远端是空仓库时，会把项目起点推成默认分支，这样 PR 才有目标分支。推之前会再核对一次远端确实是空的。

合并永远由人在 GitHub 上点。GitHub 免费组织的私有仓库设不了分支保护，这道护栏由系统自己把守；如果以后升级到付费套餐，可以在 GitHub 上再设分支保护和必审规则，作为第二道防线。

## GitHub 闭环

交付开了 PR 之后，守护进程接着盯它；GitHub 上打了标签的 issue 和定时任务也能变成新任务。这几样都只用部署级的连接（GitHub App 优先，其次部署级令牌），不借成员自己的连接；App 要给的权限见上文。

- **盯交付的 PR**：任务页和项目页的「交付的 PR」卡显示 PR 状态、CI 和评审意见。守护进程按情况定节奏：CI 在跑每 1 分钟看一次，跑完每 5 分钟，PR 关了每 30 分钟（3 天后不再看），合并了就停；出错时逐次退后。请求带条件头，没变化不占 GitHub 的额度；剩余额度低于 50 时等到重置。App 没给 CI 那几项读权限时，PR 状态和评论照看，CI 一栏写明缺哪项权限。
- **AI 跟进**：交付开 PR 时会单独问一句"授权 AI 跟进这个 PR？"（命令行默认授权，加 `--autofix off` 不授权）。授权之后：
  - CI 没过，AI 带着没过的检查和 Actions 日志的末尾去修，修好推回同一个 PR，最多 2 轮。日志是外部文本，不当指令。
  - 有交付权的成员在 GitHub 上「Request changes」，连同那次评审的行内评论直接转成修正，改好同样推回。
  - 推回前和交付时一样过关：交付时签过收或高风险的任务，新版本也要签过才推；交付前钩子和推送护栏照常。
  - 不自动修、改为发事项问人的几种：已经修满 2 轮、会撞预算闸门、PR 分支上有别人推的提交、授权的人已被停用或令牌已吊销。答「不用修」就不再管这个提交上的失败，别的答复转成修正。
  - 卡片上一行写着现在是谁授权的；有交付权的人可以「收回授权」或「由你授权 AI 跟进」。收回只管以后，已经交给 AI 的那一轮照旧做完（要当下停，暂停任务）。
  - 合并永远由人在 GitHub 上点。
- **评审意见**：卡片上每条意见可以「让 AI 按这条改」（以点的人的名义）或「不用管」（只记在看板上，不回 GitHub），「不用管」可以撤回。不是成员的意见分开列，不会触发要花钱的动作；机器人的不列。
- **项目整体交付的 PR**：CI 没过时，按交付人的授权起草一份修复任务（最多 2 轮，按项目的自动化挡位走）；修复任务合并后，要有人再交付一次项目，PR 才会更新。
- **GitHub issue 入口**：负责人在「项目设置 → Issue 与定时任务」填仓库和标签（命令行 `project issues <项目> --repo <owner/repo> --label <标签>`，`--off` 关掉）。守护进程每 5 分钟看一次，带这个标签的 issue 每条起草一份添加任务的草稿：
  - 一律要人批准，自动挡下也一样；批准事项开头写明来源、作者和链接；issue 正文是外部文本，交给 AI 时写明不是指令。
  - 作者对得上项目里的人，需求记在他名下（做完由他签收）；否则记在开入口的人名下。
  - 同时在路上（起草中、等批、排队）的最多 3 条；放弃过的不会再起草；issue 关了或摘了标签，还在排队的会被拿掉。
  - 只读 GitHub：不回帖、不改标签。标签就是授权的那道门，别把它写进 issue 模板。
- **定时任务**：同一页添加，选每天 / 每周 / 每月或写 cron（五段，按部署时区；也认 `@daily` 这类写法）；命令行 `project schedule <项目> add --name <名字> --cron "0 9 * * 1" --brief "<要做什么>"`（`on` / `off` / `rm <id>`）。到点起草一份添加任务，和人提的需求一样走自动化挡位。错过的只补一次；上一次起草的还没批完，这一次就跳过。

## 联网源的凭据

私有的 npm / PyPI 源、内网镜像要认证时，凭据配在**源**上，由出网代理在请求里替工具带上；沙箱里的代码看不到它。

```bash
node src/cli.mjs sources cred add <源 id> --key-file <文件>            # 文件里是整个请求头的值，例如 "Bearer <令牌>"
node src/cli.mjs sources cred add <源 id> --key-file <文件> --basic    # 文件里是"用户名:密码"
```

- 源 id 在「设置 → 联网目录」里看。凭据加密存进库（和连接同一把主密钥），录入后谁都看不到原文。
- **默认只读**：配了凭据的源，只在读请求（GET、git clone）上带凭据；并且放行这个源的项目，它放行的所有源都只能读（POST、PUT 一类被拦下），免得任务里的代码借着凭据往外发东西。确实要写的源，加 `--allow-write`。
- 撤销：`sources cred revoke <凭据 id>`。

## 项目规则、Skill、钩子与 MCP

**项目规则**

- 从仓库根到这一步要改的目录，每一层至多取一份：`AGENTS.override.md`，没有就 `AGENTS.md`，再没有就 `CLAUDE.md`。根在前、越深越优先，合计 32 KiB；超了先保住最深的那层，并写明跳过了哪几份。读的是提交过的版本。执行器读写到别的目录时，那一层的规则附在工具结果后面给它。
- 规则交给执行器和验收员，并写明是仓库提供的：不能覆盖契约、扩大范围或放宽验收标准。
- 规则文件由人维护：执行器改了，交接时被打回；契约的可动路径点名了那份文件的除外。
- 每一步开跑前，规则内容或已定的约定有变化，就对着已定的约定比一遍；有冲突，挂一条事项给负责人。
- 「项目设置 → 项目规则」：能看项目的人都能看；负责人能新建、编辑、删除，保存就是在项目分支上提交一次，作者是改的人。已经开工的任务看不到新改动，从之后开工的任务起生效。

**Skill**

- 一个目录加一份 `SKILL.md`（名字、描述、正文），可以带参考文件。
- 三层：部署级 `.superintern/skills/`（管理员用 `skill add <目录>` 装）、项目级 `.superintern/projects/<项目 id>/skills/`（`skill add <目录> --project <id>`）、仓库里的 `.agents/skills/`（没有时认 `.claude/skills/`）。同名时部署 > 项目 > 仓库。
- AI 每一步先只看到名字和描述（合计 8000 字符，超了按与这一步的相关度排）；任务或步骤里点了名字的一定给；写了 `disable-model-invocation` 的只在点名时给。AI 用得上时再取全文；部署级、项目级的连同参考文件复制进工作区的 `.si-skills/`，不进提交，里面的脚本只在沙箱里跑。
- 停用：负责人在「项目设置 → Skill」逐份开关（只管本项目），或 `skill off <层>:<名字> --project <id>`；管理员不带 `--project` 就是对所有项目。停掉一份时，被它顶掉的同名几份一起停。

**策略钩子**

- 四个时机：工具调用前（`PreToolUse`）、交接前（`PreHandoff`）、合并前（`PreMerge`）、交付前（`PreDeliver`）。
- 写法与 Claude Code 的 hooks 相同，现有的钩子可以直接用：

  ```json
  {"hooks": {"PreToolUse": [{"matcher": "Bash", "hooks": [{"type": "command", "command": "./.superintern/hooks/check.sh", "timeout": 30}]}]}}
  ```

  stdin 收一段 JSON（事件名、工具名、工具参数等）。exit 2 = 拦下，理由取 stderr；exit 0 时读 stdout 里的 `hookSpecificOutput.permissionDecision`（`allow` / `deny` / `ask`）。几个钩子都匹配时都跑，按 deny > ask > allow 合并。`matcher` 认系统的工具名，也认 Claude Code 的叫法（`Bash`、`Read`、`Write` 等）；MCP 工具写 `mcp__.*`。`timeout` 默认 30 秒，最长 600 秒。
- 放在哪、谁来信：
  - 部署级 `.superintern/hooks.json`、项目级 `.superintern/projects/<项目 id>/hooks.json`：只有能登录服务器的人改得了，在主机上跑。按内容核准：`hook list` 看，`hook trust` 核准；命令或它点到的脚本一改，就要重新核准，没核准的不跑。
  - 仓库里的 `.superintern/hooks.json` 和 `.claude/settings.json`（后者只认 `PreToolUse`）：从任务开工时的提交读，只在沙箱里只读跑。任务里改了钩子文件或钩子脚本，仓库钩子就不跑、按拦下处理，交接时打回。
- 钩子自己出错时：工具调用前、交接前默认放行（单个钩子写 `"onFailure": "block"` 就拦）；合并前、交付前一律按拦下处理。
- 钩子说拦下：工具调用前的，理由回给 AI；交接前的并进交接拒收，同一条连续三次就转成问人；合并前的挂一条事项，答复转成修正；交付前的报错、不推送。
- 钩子说要人确认：发一条「安全审批」事项，答「同意」放行这一条。交付前的钩子要确认时，报错里带一个确认码：看板上弹窗确认，命令行加 `--hook-ack <确认码>` 重新交付；钩子说的内容变了，确认码就作废。
- 「项目设置 → 钩子」（只读）按四个时机写明：钩子说拦下、要人确认、自己出错各会怎样，并列出系统自带的检查和配置的每个钩子的状态。

**MCP**

- 配置：部署级 `.superintern/mcp.json`、项目级 `.superintern/projects/<项目 id>/mcp.json`、仓库里的 `.mcp.json`，写法同 Claude Code：`{"mcpServers": {"<名字>": {"command": "…", "args": […], "env": {…}}}}`；远程 server 写 `{"type": "http", "url": "https://…"}`。同名的，排在前面的顶掉后面的。
- 本机 server 在任务的沙箱里起，网络和凭据就是这个沙箱的。远程 server 经沙箱里的一个桥、走出网代理，要在项目的「联网」里放行它的域名。远程 server 的令牌不要写进配置：在「设置 → 联网目录」按它的地址加一个源，用 `sources cred add <源 id> … --allow-write` 配（MCP 的请求都是 POST）。配置里像凭据的环境变量和请求头不会被用到；已经提交进仓库的，要当作已泄露、作废换新。
- 批准：项目负责人或管理员在「项目设置 → MCP」，或用 `mcp check --project <id>` 把 server 起一遍、看工具说明原文，再 `mcp approve --project <id>` 批准。server 的命令、参数、环境、地址或工具清单一变，AI 就拿不到它，直到重新批准；页面上并排列出批准时和现在的两份说明。`mcp off --server <id> --project <id>` 停用（`on` 重新启用）。
- 每个工具的用法：`ask`（默认，每次调用发一条安全审批，答「同意」放行这一条）/ `auto`（直接用）/ `off`（不给 AI）。在页面的下拉框里改，或 `mcp tool <mcp__…> auto|ask|off --project <id>`。工具自己标的只读 / 可写不作数。
- 只在沙箱里跑：不用沙箱的任务拿不到 MCP 工具。结果超过 4 万字符时，只给 AI 开头一段，全文存进工作区的 `.si-outputs/`。

## 修改溯源：每处改动凭什么

不打开看板也能回答"这处改动是哪一步做的、依据契约的哪一条、谁下的指令、谁批准的"：

- **契约条款有编号**：每版契约切成一条条条款（C1、C2……）。条款文字不变，编号就不变；改了字的条款拿新编号。规划时每一步都记下它落实的是哪几条。
- **提交信息自带出处**：每个步骤的提交信息末尾有几行出处，git 和 GitHub 都把它们识别为 trailer：
  - `SuperIntern-Task` / `SuperIntern-Node`：任务与步骤；
  - `Contract`：契约第几版、谁在什么时候批准的；
  - `Clauses`：这一步落实的条款编号；
  - `Instructed-by`：给这一步下过指令或答过问的人；`Requested-by`：发起人；
  - `Trace`：看板上这一步的链接。只有在「设置 → 连接」里填了看板地址才写。
- **PR 正文带溯源表**：批准、发起、签收、交付各一行，再加一张表，列出每一步落实的条款、指令来源和对应的提交。在 GitHub 上用 squash 合并，这些信息也不会丢。
- **GitHub 账号**：每位成员可以在「成员」里填自己的 GitHub 账号和提交邮箱，也可以用 `node src/cli.mjs user git <id> --github <账号> --email <邮箱>`。管理员在「设置 → 连接」里打开 Co-authored-by 后，提交里会给批准人、下指令的人、发起人各加一行 Co-authored-by，GitHub 会显示他们的头像。这一项默认关，因为它在 GitHub 上的意思是“共同作者”。提交邮箱建议填 GitHub 的 noreply 地址。
- **从代码倒查**：任务的「改动」卡片里有个追溯框，填提交号（`HEAD~1` 这种写法也行）或 `文件:行号`，就能查出这处代码是哪一步做的、依据契约哪几条、谁说过什么、谁批准的。步骤详情里的「这一步的出处」是同一份信息。交付出去的仓库可以在命令行里查：

  ```bash
  node src/cli.mjs trace src/api/orders.mjs:42 --repo <仓库目录>
  ```

  `文件:行号` 查到的是最后改这一行的那个提交。没装 SuperIntern 的人直接看 `git log`，每个提交末尾的出处行就是同样的信息。
- 溯源表里有条款原文和答复摘录，仓库是公开的话，这些也会一起公开。
- 出处记录只能追加，不能删改。

## 备份与恢复

全部状态（任务、审计记录、花费账本、交接记录）都在 `.superintern/state.db` 这一个文件里。

- **自动备份**：守护进程默认每 24 小时备份一次，每 7 天另做一份每周备份。每份做完会当场以只读方式打开核验，核不过的不会留下。默认保留最近 7 份每日备份和 4 份每周备份。间隔可以改（0 = 关闭）：`node src/cli.mjs user setting deploy.backup_every_hours 12`。
- **例行检查**：守护进程每小时做一次快速完整性检查，每天做一次完整检查，外键也一起核对。结果写入审计记录。
- **手动备份**：`node src/cli.mjs db backup`；`db backups` 列出已有的备份。
- **恢复**：
  1. 先停掉看板、守护进程和在跑的任务。还有进程在写这个库时，命令会拒绝执行。
  2. 运行 `node src/cli.mjs db restore <备份文件>`。当前的库会先另存一份，之后再换上备份；如果备份来自旧版本，会顺带升级到当前版本。
  3. 运行 `db check --full` 核一遍。
- **主密钥不在备份里**：`.superintern/master.key` 不会进 `backups/`。把备份或库文件交给别人排查问题时，不会连带交出凭据。反过来，换机器恢复时要把 `master.key` 一起带过去，否则连接解不开，只能重新录入。建议把它另存一份在安全的地方。
- **不要在服务运行时直接复制 `state.db`**：WAL 模式下，最近的提交可能还在 `-wal` 文件里没写进主文件，直接复制会拿到不一致的副本。要用 `db backup`。
- **数据丢失窗口**：使用默认设置时，最多丢失最近一天的数据（取决于备份间隔）。要缩短，就调小间隔，或者把 `backups/` 目录同步到别的机器。只放在同一块盘上的备份防不了盘坏。

## 花费与预算

每一笔模型花费都记在一个人头上。默认记在发起任务的人头上，可以改成项目负责人或批准任务契约的人：`node src/cli.mjs user setting deploy.cost_attribution project_owner`。

预算一共四层，任何一层到了，在跑的那一步都会在下一次调用模型之前停下，并发一条事项给该拍板的人：

| 层 | 在哪里设 | 默认 |
|---|---|---|
| 任务 | 任务页「上限」 | 部署默认 |
| 项目 | 项目设置「预算与上限」 | 不设 |
| 每人每月 | 设置 → 花费（单个人），或 `deploy.person_budget_usd_month`（所有人的默认值） | 不设 |
| 整个部署每月 | `deploy.budget_usd_month` | 不设 |

- **预占**：每次调用模型之前，系统先在一个事务里，按最坏情况的花费预占额度，再连同各层闸门一起判断。几个任务同时在跑时，不会一起越过闸门。
- **被取消的调用**：中止任务或暂停全部时当场取消的那次模型调用拿不到用量，按估算记账（输入照估，输出按上限算），账上标为估算。
- **月份**：按部署时区切分（见下文「时间与日历」；没设就是 UTC）。
- **公平调度**：`deploy.max_running_per_person` 限制每个人同时在跑的任务数，0 表示不限。守护进程会在不同人之间轮流拉起任务，一个人一次提了很多任务，也不会把别人的任务压在后面。
- **查看花费**：「设置 → 花费」显示每个人本月和上月的花费，以及近 14 天的走势。成员只看得到自己那一行。命令行用 `node src/cli.mjs user spend`。

## 运行状况与公告

- **设置 → 运行状况**（只有管理员看得到）：守护进程、容器运行时、状态库、备份、完整性检查、Node 内置的 SQLite、模型服务商、联网目录里的凭据、时区与节假日、运行期自检，每一项标「正常 / 注意 / 有问题」，有问题的排在前面，并写了要做什么。有「注意」或「有问题」时，侧栏这一项带一个小圆点。
- **运行期自检**：守护进程定期核对几条应该一直成立的事：每个没结束的任务说得出在等谁、花费越过上限时闸门确实拦过、任务的工作区没有罩住状态库和主密钥、占着任务的进程还活着等。有一条不成立就合并成一条通知发给管理员。命令行：`node src/cli.mjs invariants`（加 `--run` 当场查一遍）。
- **值得看一眼的变化**：例如某个模型的上下文窗口偏小、有步骤反复撞自动整理线、原有测试被改弱的次数多起来了。点「知道了」收起；情况消失后再出现会重新提醒。
- **公告**：同一页下方，发给所有人，看板顶部一条横幅。
- **存活探针**：`GET /healthz` 不用登录，进程在、库能读就回 `{"ok":true}`，否则 503。

## 时间与日历

「设置 → 时间与日历」里，管理员设**部署时区**（如 `Asia/Shanghai`）和**节假日与调休**；命令行是 `node src/cli.mjs calendar`。

- 路由表里的超时「1bd」（一个工作日）、值班表几点交接、月度预算哪天翻篇，都按部署时区算。没设就按 UTC，中国的部署会差 8 小时，运行状况会提示。
- 节假日一行一条：`2026-10-01..2026-10-07 国庆`；调休补班写 `2026-10-11 班`。表里的日子快用完时运行状况会提示补下一年。
- 每个人可以在同一页设自己的时区：看板上的时刻按它显示，他的工作时间和状态报告的钟点也按它算（见下文）。没设就跟部署时区。
- 值班代班（某几天整天由某人值）在决策路由的值班表下面添加，或 `routing swap`。

## 监督模式与审批门禁

系统发给人的每一类信号分三档介入方式：**决策**（要人定，挂成事项）、**通知**（推给人，不挡路）、**备案**（只留记录，看板上看得到）。

- **监督模式**：每个项目在「项目设置 → 监督与审批」选一种，没选的用部署默认 `deploy.oversight_mode`（`full` / `spot` / `exception`，默认 `spot`）。
  - **逐项审批**：AI 自己定的做法、计划自己改的地方都要你点头，点头之前不合并；每一步的进展都推给你。
  - **抽检**（默认）：该你拍板的事等你拍板；AI 自己定的做法、计划自己改的地方推给你看，不拦着它；每一步的汇报只留记录，任务级的进展照推。
  - **例外管理**：只在出了偏离常规的事时打扰你：Ⅰ 级的规格取舍按 AI 提的默认直接走、事后告诉你；日常进展只留记录。
- **底线**：契约与方案批准、签收、意见冲突、花钱的闸、安全审批、交回给人的故障，在任何模式下都要人定；系统替人定了（超时、按默认直接走）、以你的名义对外动作、安全边界被系统改了、部署出故障，在任何模式下都会通知，个人调不掉。
- **审批门禁**：负责人在同一页列出必须有人点头才能跑的命令，一行一条，`*` 代表任意一串字符、`?` 代表一个字符，整条匹配、不分大小写（例如 `git push*`、`*migrate*`、`kubectl apply*`、`psql*`）。包在 `sh -c "…"` 里、或用 `&&`、`||`、`;`、`|` 连起来的每一段都比；每段开头的环境变量赋值和工具路径会先去掉（`PGPASSWORD=x psql`、`/usr/bin/psql` 都认得出）。AI 跑到命中的命令前停下，发一条「安全审批」事项，答「同意」放行这一条，一模一样的命令之后不再问。清单默认为空；单独一个 `*` 不收。页面上可以拿没保存的清单"试一条命令"。
- **安全审批**：审批门禁命中、策略钩子要人确认、MCP 工具要批准，都发这一类事项。它没有默认答复，不会因为超时被替人定，没人答就一直停着。路由表里没有这一行时，发给「系统卡住」那一行的人；要交给别人，在「项目设置 → 决策路由」加一行（内置模板已经带上）。
- **系统不替人拍板的几类**：结构矛盾、方案批准、签收、上限追加、联网放行、意见不一致、安全审批、系统卡住都没有默认答复；到期升级，再没人答就一直等着，并通知原来的收件人和任务负责人。

## 通知与推送

- **通道**：每个人在「设置 → 成员」挂自己的通道（ntfy、飞书、钉钉、企业微信、邮件）。`.env` 里的部署级通道（`NTFY_URL`、`MAIL_TO` 等）只给没挂个人通道的管理员用，以及一件事的收件人一个都推不到时兜底。都没有的，事项照样在看板收件箱里。
- **「我的通知」**（设置里）：每一类信号自己选「推送」还是「只留记录」；底线类写着"总是推送"，改不了。收件箱的「通知」卡片里，每条写明归哪一类，可以一键"这一类以后不推送给我（所有项目）"。
- **紧急程度**：紧急的马上推：Ⅲ 级事项（签收除外）、安全审批、已经升级或离时限不到 2 小时的事项、以你的名义对外动作、安全边界被系统改了、部署出故障。其余都不紧急，包括签收和抄送给你的。
- **工作时间**：不紧急的只在你的工作时间里推，默认工作日 9–18 点，按你自己的时区和部署的节假日表算，支持跨午夜。
- **汇总推送**：不紧急的攒起来，每隔一段时间（默认 60 分钟）合成一条，按种类分组，同一项目的挨着放；只攒到一件时照原样推。
- **推送限额**：一小时里打断你的次数（单条和汇总各算一次）默认最多 4 次；到了之后，后面的排进下一次汇总的最前面。Ⅲ 级事项（签收除外）和部署出故障不受限。
- 以上几项每个人在「我的通知 → 什么时候推」里改自己的，页面上显示最近 7 天被打断了几次。管理员在同一处改部署默认，对应 `deploy.work_start_hour`、`deploy.work_end_hour`（24 = 到午夜）、`deploy.work_days_only`、`deploy.digest_every_min`（0 = 不攒）、`deploy.push_cap_per_hour`（0 = 不限）。
- **事项链接与快速答复**：每条推送末尾带一个链接。单条链到那一件，打开只装那一件，手机上也能读能答（规格取舍、结构矛盾、系统卡住、意见不一致）；签收、安全审批、方案批准、上限追加、联网放行、交付会链到完整的任务页。汇总链到收件箱。链接地址取「设置 → 连接」里的看板地址（`deploy.board_url`），没填就用看板启动时的地址（团队模式是 `--public-url`，本机模式是 `127.0.0.1`）；单独跑守护进程又没填时不带链接。链接里不带凭据，打开照常登录。
- 定时推送全量待办摘要的 `daemon --digest-every` 已不再使用；全量清单看收件箱或 `digest` 命令。

## 邮件通道与邮件答复

**发信**：在 `.env` 里填 `SMTP_URL` 和 `MAIL_FROM`，就有了邮件通道；成员在「设置 → 成员」登记个人邮箱（命令行 `user channel <id> --email <邮箱>`），`MAIL_TO` 是部署级收件邮箱。两项没填时，登记的邮箱标"还推不出去"。

- `SMTP_URL` 的写法：`smtps://用户:密码@smtp.example.com:465`（直接 TLS）；`smtp://用户:密码@smtp.example.com:587`（先连上再 STARTTLS，服务器不支持就不发，不降级）；`smtp://127.0.0.1:25`（本机中继，只有本机地址允许明文，明文上不发密码）。用户名、密码里的 `@ : /` 要写成 `%40 %3A %2F`。
- 证书照常校验；审计里只记收件人的域名。

**邮件答复**：再填 `IMAP_URL`，就能直接回推送邮件来答。

- `IMAP_URL` 的写法：`imaps://用户:密码@imap.example.com:993`；文件夹默认 INBOX，要换就写在路径上（`imaps://…/Replies`）；`imap://…:143` 走 STARTTLS，服务器不支持就不收。守护进程每分钟收一次没读过的信，处理完标为已读，不删。
- 回信寄到 `MAIL_REPLY_TO`（没填就是 `MAIL_FROM`），这个地址的信要能在 `IMAP_URL` 的邮箱里收到。邮箱支持加号别名的（Gmail、Outlook、Fastmail、自建 Postfix 等），写成 `reply+{token}@example.com`，回信不带 In-Reply-To 的客户端也认得出。
- 能回信答的只有规格取舍、结构矛盾、系统卡住三类，而且只对等你答的人；其它事项、抄送、汇总的信里会先写明"回信没用"。
- 回信最上面写一句就行（例如"选 B"），下面引用的原文不用删。只算第一次回信，推送后 72 小时内有效；之后要改，到看板上改。
- 回信要从登记的邮箱发出；收信服务器判了 DMARC / SPF 失败的不算。没算上的回信（过期、已经答过、认不出是哪件事等）会收到一封说明和链接；说明只回给登记过的邮箱，同一地址一小时最多 10 封。自动回复、退信、群发不处理。
- 收不到信（`IMAP_URL` 配错、服务器连不上）时告诉管理员一次，恢复时再告诉一次。

## 状态报告

一段时间里发生了什么，按人现算，不调模型：

1. **出事了没有**：部署出故障、安全边界被系统改了、硬失败、项目停下来、超时一路没人接、触到花费或次数上限；这几类都没有，才写"没有出事"。
2. **没等你拍板就定下的**：超时按默认、别人动了你的事、AI 自己定的、计划自己改的、AI 加的任务、自动升档、以你名义对外的动作、系统小修；调成只留记录的也汇总进来，并写明没推送过。
3. **进展**：合并了哪些任务。
4. **花费**和还等你答的事项数。

- 范围：成员看发给自己的和自己参与的项目；全部项目只给管理员（管理员默认看全部）。详略：只报异常 / 摘要（每段最多 5 条）/ 详细。
- 看板侧栏「状态报告」页随时看：最近 24 小时 / 7 天 / 30 天 / 上个月，条目直达对应的事项、任务或项目。命令行：`node src/cli.mjs report [--since 24h|7d|<日期>] [--detail exceptions|summary|full] [--all] [--user <id|名字>]`（`--all` 和看别人的只给管理员）。
- **定期推送**：每个人在「我的通知」里设频率（不发 / 每天 / 每周几）、钟点和详略，没设的跟部署默认：`deploy.report_every`（`auto` / `off` / `day` / `week`）、`deploy.report_day`（1 = 周一 … 7 = 周日）、`deploy.report_hour`、`deploy.report_detail`（`auto` / `exceptions` / `summary` / `full`）。`auto` 按默认监督模式：逐项审批每天一份摘要，抽检每周一份摘要，例外管理每周一份只报异常；默认是周一 9 点。钟点按各人时区，那天不是工作日就顺延到下一个工作日。每份接着上一份的结束，不漏不重。报告单条推、不并进汇总，只在工作时间里推、计入推送限额；太长的截断，完整的在看板上。
- **「你不在时」**：离开看板 8 小时以上再回来（页面打开着、有操作才算在看），收件箱顶上给出这段时间发生了几件事和直达那段报告的链接。

## 日志与追踪

- **给人看的日志**：守护进程写 `.superintern/logs/daemon.log`，每个任务进程写 `.superintern/logs/<任务>-<时刻>.log`，看板上「日志」按钮显示的就是后者的尾部。
- **结构化日志**：守护进程、看板和任务进程还会写一份 JSON 行日志，在 `.superintern/logs/jsonl/` 下，每个进程每天一个文件。每行带这些字段：
  - 时间、级别、原文；
  - 进程种类与 pid；
  - 任务 id 与步骤 id；
  - trace id：守护进程每一拍起一个，它拉起的任务进程沿用同一个。所以同一次拉起的守护进程日志和任务日志，可以按 trace id 对起来。
- **自动清理**：守护进程每天做一次。
  - 删掉超过保留天数的任务日志和 JSON 行日志（默认 14 天，可改：`node src/cli.mjs user setting deploy.log_keep_days 30`）。
  - `daemon.log` 超过 10 MB 时，复制成 `daemon.log.1`，原文件清零。
  - 已合并或已归档的任务，删掉工作区里的依赖目录（`node_modules`、`.venv` 等），并把腾出的空间记进审计。不想删就设 `deploy.clean_merged_deps false`。任务被重新打开时，依赖会重新安装。
- **密钥不落盘**：写进库、日志、模型调用录制的文字，和发出去的通知，都会先去掉密钥，换成 `[redacted]`。认得出的有三类：
  - 常见的密钥形状：API key、GitHub 令牌、AWS key、私钥、JWT 等；
  - `Authorization` 请求头和网址里的口令，只去掉值、保留前缀；
  - 按值认：`.env` 里名字以 `_KEY`、`_TOKEN`、`SECRET`、`PASSWORD` 等结尾的变量的值，以及「设置 → 连接」里录入的凭据。
  - 在对话里贴的 key 也会在存进库之前被去掉，代理和模型都看不到它。密钥请放进「设置 → 连接」或 `.env`，不要贴进对话。
- **OTLP 追踪导出（可选）**：设了 OpenTelemetry 的标准环境变量 `OTEL_EXPORTER_OTLP_ENDPOINT`（或 `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`）才会导出，按 OTLP/HTTP JSON 发送。
  - 每个执行步骤一个 span，每次模型调用一个子 span。
  - 模型调用的属性按 OTel GenAI 语义约定填写：模型、token 用量、花费。
  - **不导出提示词和回复内容。**
  - 收集端要认证时，用 `OTEL_EXPORTER_OTLP_HEADERS` 配置请求头。
  - 设 `OTEL_SDK_DISABLED=true` 关闭导出。

## 升级

1. **备份**：迁移前系统会自动把整个库备份到 `.superintern/backups/`。想自己再留一份，就在升级前运行 `node src/cli.mjs db backup`。
2. **换代码**：替换代码，或者 `git pull`。
3. **迁移**：执行一次 `node src/cli.mjs init`（或者任何一条命令）。系统会按 `PRAGMA user_version` 逐级跑迁移，迁移不会删数据。每一级迁移和版本号写在同一个事务里，中途失败就停在原来的版本，库不会只改了一半。如果是已有数据不满足新版本的约束，报错会写明是哪张表、哪条约束、哪几行。
4. **更新镜像**：如果新版本换了沙箱镜像的 tag，重新跑一次 `setup`，把缺的镜像建出来。

**从 0.3.x 升到 0.4.0 要知道的：**

- **安全修复，沙箱容器会重建**：沙箱里的代码原来能往工作区的 `.git` 写钩子，下次宿主机上的 git 操作就会执行它。现在 `.git` 对沙箱只读，宿主机上的 git 不执行仓库里的钩子和 fsmonitor。旧规则起的容器会被自动删掉重建；项目自己的 git 钩子（husky、pre-commit 等）在 SuperIntern 做的提交里不再执行。
- **联网目录里工具配置的凭据不再放进沙箱**：以前放行过这个源的项目，任务里的代码读得到这些凭据。建议先在那个源上换一个新凭据，再按上文「联网源的凭据」配；运行状况会列出哪些源要处理。没处理之前，要认证的安装会失败。
- **库会升级并收紧约束**：迁移中途已有数据不满足新约束时，整个迁移回滚、库停在原来的版本，报错写明哪张表、哪条约束、哪几行。迁移前系统会先自动备份。
- **默认打开的几样**：验收员与执行器同一家时换一家（`.env` 里有多家 key 时花费会跟着变）、上下文整理（120k）、每 24 小时备份、日志保留 14 天、已合并任务的依赖目录自动删除。上文各节写了怎么改。
- **令牌**：新签的命令行令牌默认 90 天过期（`deploy.cli_token_days`，0 = 不过期）；升级前签的不受影响。团队模式的浏览器 cookie 里现在放的是会话，不再是令牌本身。
- 设了 `HTTPS_PROXY` 的机器，模型调用也会走这个代理（`SUPERINTERN_IGNORE_ENV_PROXY=1` 关掉）。

**从 0.4.x 升到 0.5.0 要知道的：**

- **库会自动升级，先自动备份**：第一次运行任何命令时，库从 0.4.x 的版本逐级迁移，迁移前整库备份到 `.superintern/backups/`（文件名带 `pre-v47`）。几张表（事项、路由表、令牌、推送队列）会重建，库大时要多等一会儿。升级之后 0.4.x 的代码会拒绝打开这个库；要退回旧版本，先换回旧代码，再 `node src/cli.mjs db restore <那份备份>`。沙箱镜像没变，不用重跑 `setup`。
- **仓库里的这些文件开始生效**：`AGENTS.md`（以及 `AGENTS.override.md`，都没有时的 `CLAUDE.md`）会整份交给执行器和验收员；`.agents/skills/`、`.claude/skills/` 里的 skill 会列给 AI；`.superintern/hooks.json` 和 `.claude/settings.json` 里的 PreToolUse 钩子会在沙箱里跑，可能拦下 AI 的操作，合并前、交付前的钩子出错按拦下处理；`.mcp.json` 里的 server 只列出来，负责人批准之前不会给 AI。升级前请看一眼项目仓库里有没有这些文件、内容是不是你想让 AI 遵守的。另外，AI 改这些规则文件和钩子文件会被打回，除非契约的可动路径点名了它们。详见上文「项目规则、Skill、钩子与 MCP」。
- **推送变少、变晚**：要推给人的事改为按人排队。默认只在工作时间（工作日 9–18 点）推不紧急的，攒成每 60 分钟一条的汇总，每人每小时最多打断 4 次；紧急的照旧马上推。工作时间按每个人自己的时区算，没设就按部署时区，部署时区也没设就按 UTC —— 中国的部署请先在「设置 → 时间与日历」设好部署时区，否则工作时间会差 8 小时。每个人设的时区现在也决定他的工作时间和状态报告的钟点，不再只影响显示。想回到以前那样有就推：把 `deploy.digest_every_min` 和 `deploy.push_cap_per_hour` 设为 0，`deploy.work_start_hour` 设为 0、`deploy.work_end_hour` 设为 24、`deploy.work_days_only` 设为 `false`。
- **部署级通知通道不再收到每条事项**：`.env` 里的 `NTFY_URL` 等现在只给没挂个人通道的管理员用，以及收件人一个都推不到时兜底。以前靠一个共用的部署级通道看通知的成员，请在「设置 → 成员」挂自己的通道。
- **每一步的汇报不再推送**：默认监督模式是抽检，每一步的汇报只留记录（看板上照样看得到）；任务做完、停下来等人、等交付照旧推。想照旧每一步都推，把项目的监督模式改成逐项审批（「项目设置 → 监督与审批」）。
- **开始收到每周状态报告**：`deploy.report_every` 默认 `auto`，抽检下是每周一 9 点（按各人时区，在工作时间里推）一份摘要。不想要：每个人在「我的通知」里关掉，或管理员 `node src/cli.mjs user setting deploy.report_every off`。
- **守护进程的 `--digest-every` 被忽略**：计划任务或 systemd 里还带着它的，启动时会打一行说明，照常运行；可以从启动参数里删掉。
- **有些事项不再按默认结案**：结构矛盾、方案批准、签收、上限追加、联网放行、意见不一致、安全审批、系统卡住一律没有默认答复，到期只升级，然后一直等人。升级时还开着的这几类事项也一样：迁移会去掉它们存着的默认答复，Ⅰ 级的改成 Ⅱ 级。另一方面，规划阶段提的问题现在有时限了（以前一直等），过了时限按事项的级别升级或按默认走。
- **新的决策类型「安全审批」**：钩子要人确认、MCP 工具要批准、命中审批门禁时发这一类。已有的路由表里没有这一行时，它发给「系统卡住」那一行的人（再没有就按结构矛盾）。想交给别人，在「项目设置 → 决策路由」加一行；内置模板已经带上。
- **执行器的输入多了一段仓库地图**：每一步开头最多 2048 token，花费会略有增加。不想要：`node src/cli.mjs user setting deploy.repo_map_tokens 0`。
- **GitHub App 要多给几项读权限**：盯 PR 的 CI 要 Checks、Commit statuses、Actions 读；GitHub issue 入口要 Issues 读。在 App 设置里加上，再到组织的安装页接受新权限。没给的话，PR 的状态与评论照看，CI 一栏标出缺哪项权限。升级前开的 PR 系统不盯，只有升级后新开的才会。
- **命令行交付默认授权 AI 跟进**：`deliver … --pr` 开的 PR，CI 没过时 AI 会自动修并推回同一个 PR（最多 2 轮）。不想要就加 `--autofix off`；看板上交付时会单独问。
- **谁能暂停任务变了**：参与过任务的人（事项发给过他，或他答过）也能暂停；继续由负责人或按暂停的人点；中止仍只给负责人。
- **推送里带事项链接**：用 `start` 脚本或 `web --daemon` 起的，链接按看板自己的地址生成（本机模式是 `127.0.0.1`，要走 SSH 隧道才打得开）。单独跑守护进程，或想让链接用别的地址，在「设置 → 连接」填看板地址（`deploy.board_url`）；注意这个地址也会写进提交与 PR 的溯源链接。
- **新的可选配置**：邮件通道与邮件答复（`.env` 的 `SMTP_URL`、`MAIL_FROM`、`MAIL_TO`、`IMAP_URL`、`MAIL_REPLY_TO`，见 `.env.example`）；部署级的 skill、钩子、MCP 配置（`.superintern/skills/`、`.superintern/hooks.json`、`.superintern/mcp.json`）；上文各节里新的部署设置。都不配也能照常运行。

## 日常命令

```bash
node src/cli.mjs digest                 # 我的待办（谁答、等谁、到期）
node src/cli.mjs questions              # 开放的问题一览
node src/cli.mjs answer <qid> "..."     # 答复
node src/cli.mjs say <task> "..."       # 修正 / 新指令 / 补充信息；加 --urgent 打断正在执行的步骤
node src/cli.mjs signoff <task> --accept | --reject "理由"
node src/cli.mjs replay <task>          # 只凭审计记录和状态库复盘
node src/cli.mjs sandbox --reap         # 清理遗留的容器和派生镜像
node src/cli.mjs bind                   # 三档各绑了什么；bind set heavy=<服务商/模型> 改
node src/cli.mjs bind role verifier <服务商/模型>   # 某个角色单独绑；bind fallback standard=<服务商/模型> 配备用
node src/cli.mjs user spend             # 每个人本月花了多少
node src/cli.mjs invariants             # 运行期自检的结果
node src/cli.mjs db check               # 状态库完整性检查；db stats 看体量与慢语句
node src/cli.mjs endpoint               # 服务商与 key 填没填；endpoint test <id> 测试连接
node src/cli.mjs catalog check          # 模型目录漂移检查（守护进程默认每 7 天自动查一次）
node src/cli.mjs report --since 7d      # 状态报告：这段时间出事了没有、没等你拍板就定下的、进展、花费
node src/cli.mjs rewind <task> <步骤>   # 从做完的这一步重来：先看预览，加 --yes 才生效
node src/cli.mjs skill list             # skill；hook list / hook trust 管宿主上的钩子
node src/cli.mjs mcp list --project <id>   # MCP server 的状态；mcp check / mcp approve 检查并批准
node src/cli.mjs project issues <id>    # GitHub issue 入口；project schedule <id> 管定时任务
```
